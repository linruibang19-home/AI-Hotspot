# AI Hotspot 方案执行与变更控制

> 文档状态：已确认
> 目的：保证后续原型、架构和代码严格依据方案推进，同时允许经过审批的合理修订。

## 1. 权威顺序

出现冲突时，按以下顺序处理：

1. 产品负责人最新明确确认的决策；
2. 《已确认决策》和已批准 ADR；
3. 已确认的产品、领域、架构、数据、接口和测试文档；
4. 已冻结原型；
5. 当前实现代码；
6. 原始开发方案与 AI PULSE 原型等历史参考。

代码与方案冲突时，不能默认以代码为准。先确认应修方案还是修实现。

## 2. 不允许的执行方式

- 不一次性生成整个系统；
- 不跳过方案直接增加产品功能；
- 不因框架便利改变业务规则；
- 不擅自重做原型视觉和导航；
- 不使用 Mock 结果冒充真实业务完成；
- 不把前端隐藏当成权限；
- 不先召回私有数据再做结果过滤；
- 不绕过 Outbox/Inbox 直接实现不可靠异步；
- 不把多个无关任务混入同一分支和提交；
- 不在未验证时宣布里程碑完成；
- 不使用破坏性 Git 操作覆盖用户修改。

## 3. 每项任务的输入模板

开始任务前必须明确：

```text
任务编号
任务目标
对应需求/决策
涉及页面
涉及服务
涉及数据表
涉及 API/事件
权限与安全要求
验收条件
明确不修改的范围
```

缺少关键输入时，先补文档或向产品负责人确认。

## 4. 标准执行循环

```text
确认任务与方案
→ 检查 Git 工作树
→ 创建任务分支
→ 编写/更新契约与测试
→ 小步实现
→ 本地验证
→ 浏览器和视觉检查（涉及 UI 时）
→ 安全/权限/幂等检查
→ 更新文档和追踪表
→ 查看 git diff
→ 提交修改摘要和证据
→ 产品负责人审核
→ 合并和里程碑记录
```

## 5. 阶段门禁

### 方案门禁

- 需求、业务规则和待决策项明确；
- 页面、数据、权限和接口无冲突；
- 产品负责人确认进入原型或开发。

### 原型门禁

- 严格继承现有视觉基线；
- 页面正常、加载、空、失败和无权限状态齐全；
- 桌面和移动端通过；
- 修改前后对照已审核；
- 冻结 `prototype-v1`。

### 工程门禁

- Git 基线存在；
- Docker Compose 基础服务可运行；
- 健康检查、日志和测试框架存在；
- 密钥和数据不进入仓库。

### 功能门禁

- 业务验收通过；
- 单元、集成和必要 E2E 通过；
- 权限、审计、错误和恢复路径通过；
- API/事件/迁移文档更新；
- 无无关改动。

### 里程碑门禁

- 路线图退出条件全部有证据；
- 无未处理 P0/P1 缺陷；
- Git Tag 只在审核后创建；
- 未达到条件时保持“进行中”，不得为了进度标记完成。

## 6. 需求追踪

后续建立唯一需求编号，例如：

```text
PROD-CONTENT-001  游客浏览精选
PROD-EVENT-001    内容跨事件关联
SEC-RAG-001       检索前权限过滤
ASYNC-001         Transactional Outbox
MAIL-001          每日简报
```

追踪矩阵至少包含：

| 需求 | 决策 | 页面 | API/事件 | 数据表 | 测试 | 里程碑 | 状态 |
|---|---|---|---|---|---|---|---|

没有追踪项的新增功能不得悄悄进入实现。

## 7. 变更控制

### 普通修订

文字澄清、错误修复和不改变行为的细化，可以在任务分支更新文档并说明。

### 重大变更

以下情况必须先形成决策或 ADR：

- 修改产品范围；
- 改变用户权限；
- 改变公开准入或版权策略；
- 改变现有原型整体布局和视觉方向；
- 改变数据库核心关系；
- 更换 RabbitMQ、PostgreSQL 或服务边界；
- 引入新的外部数据源；
- 增加高风险 Agent 工具；
- 改变部署形态。

重大变更记录：背景、候选方案、选择、原因、影响、迁移、回滚和批准人。

## 8. 完成证据

任务交付至少报告：

- 修改文件；
- 关键设计和实现；
- 运行命令；
- 测试结果；
- 页面截图或交互检查（UI 任务）；
- API/消息样例（后端任务）；
- 数据迁移结果（数据任务）；
- 安全、权限、幂等和恢复验证；
- Git 分支与提交；
- 已知限制。

## 9. 暂停条件

出现以下情况时不得自行扩大范围：

- 方案存在互相冲突的已确认规则；
- 需要新的外部账号、密钥、预算或授权；
- 需要公开发布、推送或远程仓库写入；
- 会覆盖用户未提交修改；
- 涉及不明确的版权或私有数据；
- 结构性 UI 改动尚未确认；
- 任务需要引入未批准基础设施。

此时应报告证据、影响和可选方案，等待产品负责人决定。

## 10. 执行承诺

严格执行不等于方案永远不修改，而是：

- 当前已确认内容不能被实现过程悄悄改变；
- 新证据出现时通过正式变更流程修订；
- 每项完成状态都有验证证据；
- 每次修改都可由 Git 追溯和回退；
- 产品负责人始终掌握重大范围、视觉和架构决策。
