# AI Hotspot Git 版本管理方案

> 文档状态：已确认
> 项目根目录已于 2026-07-17 初始化本地 Git，默认分支为 `main`。当前未配置远程仓库，未经用户授权不会推送。

## 1. 目标

- 原始参考文件、方案、原型和代码均可追溯；
- 每项任务可以独立审查、测试和回退；
- 防止模型或开发过程覆盖用户已有改动；
- 里程碑具有可复现版本；
- 敏感数据、运行数据和构建产物不进入仓库。

## 2. 仓库位置

Git 仓库初始化在项目根目录：

```text
D:\Dev\Autumn recruitment project\AI Hotspot
```

不在各个子服务中创建嵌套仓库。前端、Java、Python、基础设施和文档使用同一个 Monorepo。

## 3. 初始化顺序

```text
检查工作区现有文件
→ 生成 .gitignore
→ 检查无密钥、数据库和运行数据
→ git init
→ 创建 main 分支
→ 提交原始参考文件和当前项目方案
→ 创建基线 Tag
```

建议首个提交：

```text
chore: 建立 AI Hotspot 项目与方案基线
```

建议首个 Tag：

```text
planning-v1
```

首次提交前必须再次检查原始文件是否包含隐私或密钥。

## 4. 分支规范

| 类型 | 命名 | 用途 |
|---|---|---|
| 主分支 | `main` | 始终保持已审核、可验证状态 |
| 文档 | `docs/<主题>` | 方案和 ADR 更新 |
| 原型 | `prototype/<页面或阶段>` | 原型迭代 |
| 功能 | `feat/<功能>` | 新功能 |
| 修复 | `fix/<问题>` | 缺陷修复 |
| 重构 | `refactor/<范围>` | 不改变产品行为的重构 |
| 基础设施 | `chore/<范围>` | 构建、Compose、脚本和依赖 |
| 紧急修复 | `hotfix/<问题>` | 已发布版本紧急修复 |

一个分支只处理一个清晰任务。不得在功能分支顺手大规模修改无关文件。

## 5. 提交规范

采用 Conventional Commits 类型，标题可以使用中文：

```text
docs: 更新原型迭代约束
chore: 初始化 Docker Compose 基础设施
feat(source): 增加 RSS 信源试抓取
feat(content): 实现公开内容准入
fix(rag): 修复私有数据权限过滤
test(messaging): 增加重复消息幂等测试
refactor(worker): 拆分内容处理流水线
```

规则：

- 每个提交保持单一目的；
- 提交前运行该任务对应的格式化、测试和检查；
- 标题说明结果，不使用“update”“修改一下”等模糊描述；
- 复杂提交正文说明原因、方案、测试和风险；
- 数据库迁移与依赖它的代码必须在可理解的提交顺序中出现；
- 自动生成文件只有确实需要版本管理时才提交。

## 6. `.gitignore` 必须覆盖

```text
.env
.env.*（保留 .env.example）
真实密钥和凭据文件
node_modules
.next
dist/build/target
Python __pycache__、.venv、缓存
IDE 本地文件
日志和临时文件
PostgreSQL/Redis/RabbitMQ/MinIO 数据卷
Mailpit 本地数据
模型权重和模型缓存
抓取原始 HTML/XML/JSON
用户上传文件
测试报告和截图临时输出（正式基线资产除外）
```

原型基线截图如需长期保存，应放入明确的设计参考目录并确认无敏感内容，而不是继续依赖系统临时目录。

## 7. 原始参考文件保护

- `AI_PULSE_DEVELOPMENT_SPEC.md` 和 `AI_PULSE_PROTOTYPE.html` 在基线提交中保留；
- 正式迭代创建新的 AI Hotspot 文件或工程实现；
- 不直接覆盖历史参考；
- 如果确需修正历史文件，单独提交并说明原因；
- 原型每个冻结版本使用 Tag 或明确提交记录。

## 8. 合并和审核

即使当前主要由一个开发者和 Codex 协作，也按以下方式工作：

1. 从 `main` 创建任务分支；
2. 完成小步修改；
3. 运行测试和文档检查；
4. 查看 `git diff` 确认无无关改动；
5. 提供修改摘要和验证结果；
6. 经用户审核后合并到 `main`；
7. 删除已合并任务分支。

不得使用 `git reset --hard`、强制覆盖或破坏性 checkout 清理用户修改。

## 10. 远程仓库

- 当前不自动创建 GitHub/GitLab/Gitee 仓库；
- 不自动推送；
- 远程仓库名称、可见性和账号由用户确认；
- 首次推送前检查历史中不存在密钥和大文件；
- 如果仓库公开，需要再次审查参考资料、截图、内容样本和许可证；
- 产品开放注册不等于代码仓库必须公开。

## 11. 数据库迁移规则

- Flyway 迁移文件一经合并不得修改已发布版本内容；
- 修正通过新迁移完成；
- 每次迁移有对应模型、测试和回滚/恢复说明；
- 破坏性迁移必须备份并得到确认；
- 测试环境从空库执行全部迁移验证。

## 12. Git 验收

- 根目录只有一个 Git 仓库；
- `main` 工作树干净；
- `.gitignore` 阻止敏感和运行数据；
- 原始参考和当前方案有基线提交；
- 每个任务使用独立分支和小步提交；
- 每个里程碑有 Tag；
- 提交可关联任务、测试和方案；
- 未经授权无远程推送。
