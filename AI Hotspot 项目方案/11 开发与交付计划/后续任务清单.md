## 1. 优先级说明

| 优先级 | 含义 |
|---|---|
| P0 | 影响运行正确性、数据安全或发布门禁，必须立即处理 |
| P1 | 公开 Beta 前必须完成 |
| P2 | 产品质量优化，可在稳定性之后迭代 |
| P3 | 有明确数据证明需要时再做，不预先增加架构复杂度 |

## 3. 推荐执行顺序

```text
CLEAN-01 / ARCH-02 / CONTRACT-01
→ MAIL-01 / DATA-01 / OPS-01 / SEC-01 / LEGAL-01
→ UI-01 / AGENT-01 / GIT-01
→ 根据真实指标决定 ARCH-01
```

下一次开发执行代码清理、拆分和契约补齐；RAG 阶段 B 只按评测实验逐项推进，不在同一任务中重写检索链路。有目标环境后再执行 `MAIL-01/DATA-01/OPS-01/SEC-01/LEGAL-01` 并重跑 Linux 性能基线；不要重新搭建工程骨架，也不要重做已经完成的 M0～M10。

## 5. 每次任务的共同完成定义

一个任务只有同时满足以下条件才算完成：

1. 代码、迁移和配置在同一 Git 变更中；
2. Core、AI、Web 中受影响的自动化测试通过；
3. Docker Compose 中相关服务健康；
4. 用真实数据库和 HTTP 接口验证，不以静态 Mock 页面代替；
5. 数据与权限变化有审计，失败路径可观察；
6. 更新《项目进度与剩余任务》和本清单；
7. 说明已知限制，并形成可回滚的 Git 提交。
