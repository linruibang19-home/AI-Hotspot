# AI Hotspot 异步事件与可靠消息

> 文档状态：已确认（具体队列参数在工程配置中固化）

## 1. 目标与边界

RabbitMQ 是 MVP 的统一可靠异步消息队列，用于 Java 与 Python 解耦、长任务削峰、至少一次投递、延迟重试、死信和 Worker 扩展。

Redis 不承担核心可靠异步任务。MVP 不使用 Kafka。

## 2. Exchange

```text
Name: aihot.events
Type: topic
Durable: true
AutoDelete: false
```

建议另设：

```text
aihot.retry   # 延迟重试交换机
aihot.dlx     # 死信交换机
```

延迟默认使用 TTL 重试队列 + DLX。是否使用 RabbitMQ 延迟插件需单独 ADR，不能作为基础依赖假设。

## 3. 队列

| 队列 | 消费者 | 用途 |
|---|---|---|
| q.crawl.worker | Crawl Worker | 定时/手工采集 |
| q.content.worker | Content Worker | 提取、清洗和 AI 加工 |
| q.embedding.worker | Embedding Worker | Chunk 与向量 |
| q.cluster.worker | Cluster Worker | 去重、候选和事件关联 |
| q.report.worker | Report Worker | 日报、周报和研究报告 |
| q.notification.worker | Notification Worker | 邮件发送 |
| q.agent.worker | Agent Worker | 长时间 Agent 任务 |

每个主队列拥有对应重试队列和死信路由。队列 Durable，消息 Persistent。

## 4. Routing Key

```text
source.crawl.requested
source.crawl.completed
source.crawl.failed
document.fetched

content.processing.requested
content.processing.completed
content.processing.failed

embedding.requested
embedding.completed
embedding.failed

event.cluster.requested
event.cluster.completed
event.cluster.failed

report.generate.requested
report.generated
report.generate.failed

notification.send.requested
notification.sent
notification.failed

agent.run.requested
agent.run.completed
agent.run.failed
```

过去式表示已发生事实，`requested` 表示命令型请求。事件删除或重命名必须提升版本并维护兼容。

## 5. 统一消息结构

```json
{
  "eventId": "UUID",
  "eventType": "content.processing.requested",
  "eventVersion": 1,
  "aggregateType": "ContentItem",
  "aggregateId": "UUID",
  "idempotencyKey": "content-id:process:prompt-v1",
  "correlationId": "UUID",
  "traceId": "UUID",
  "occurredAt": "ISO-8601",
  "producer": "core-api",
  "payload": {}
}
```

规则：

- `eventId` 每次发布唯一；
- `idempotencyKey` 表示业务副作用唯一性；
- `correlationId` 串联同一业务链；
- `traceId` 用于全链路日志；
- `eventVersion` 为整数；
- payload 通过对应 JSON Schema；
- 消息不传密钥、大正文或文件二进制，只传对象 ID/Object Key。

## 6. Transactional Outbox

### 写入

```text
数据库事务开始
→ 保存业务数据/Job
→ 保存 outbox_event
→ 提交事务
```

### 发布

```text
Outbox Publisher 锁定 PENDING 记录
→ 发布 RabbitMQ Persistent Message
→ 等待 Publisher Confirm
→ 标记 PUBLISHED
```

发布器要求：

- 支持批量读取和 `SKIP LOCKED`；
- 发布失败递增 retry_count；
- 使用 next_retry_at；
- 多实例不重复占用同一记录；
- 即使重复发布，消费者仍通过 Inbox 幂等。

禁止在业务事务提交后直接“尽力发送”且不保存待发事件。

## 7. 消费者与 Consumer Inbox

消费者必须使用 Manual ACK 和 Prefetch，先校验消息版本和 Schema，再执行业务。

```text
收到消息
→ 查询 eventId + consumerName / idempotencyKey
→ 已成功：直接 ACK
→ 未处理：创建 PROCESSING Inbox
→ 在业务事务中执行并保存结果
→ 标记 SUCCEEDED
→ 事务成功后 ACK
```

进程在 ACK 前崩溃时消息可重新投递。以下副作用必须幂等：

- LLM 调用；
- Embedding；
- 报告生成；
- 邮件发送；
- Agent 写工具；
- 数据库状态更新；
- MinIO 文件写入。

外部 Provider 支持幂等键时必须传递。

## 8. 重试策略

默认：

```text
第 1 次失败：1 分钟
第 2 次失败：5 分钟
第 3 次失败：30 分钟
超过最大次数：进入 DLQ
```

任务可配置最大次数和延迟，但不得无限重试。

### 可重试

- 网络超时；
- HTTP 429；
- 第三方 API 5xx；
- 模型服务暂不可用；
- 数据库瞬时异常；
- SMTP 暂时不可用。

### 不可重试

- 参数或 Schema 错误；
- URL 不合法或被 SSRF 策略拒绝；
- 权限不足；
- 对象已永久删除；
- 消息版本不支持；
- 数据状态不允许执行；
- display/index 策略禁止处理。

不可重试错误直接标记失败，不经历无意义延迟重试。

## 9. 死信与人工重放

管理端必须支持：

- 按队列、类型、时间和错误筛选；
- 查看 eventId、aggregate、traceId、payload 摘要；
- 查看首次/最后错误和尝试次数；
- 跳转关联业务对象和任务；
- 标记处理、忽略或重放；
- 单条和受控批量重放；
- 重放前重新校验权限和当前数据状态；
- 记录操作者、原因、新 eventId 和结果。

重放不直接篡改 RabbitMQ 内部消息，而由 Core API 根据死信记录创建受审计的新事件，并遵守 idempotencyKey。

## 10. Job 状态

RabbitMQ 队列状态不能替代数据库 Job 状态。通用状态：

```text
QUEUED
RUNNING
WAITING_RETRY
SUCCEEDED
FAILED
DEAD_LETTERED
CANCELLED
```

前端查询数据库 Job；RabbitMQ Management 仅供受保护运维使用。

## 11. 顺序与并发

- 默认不假设全局顺序；
- 同一 Aggregate 需要顺序时使用状态版本、乐观锁或业务序列；
- Worker 处理前检查当前状态是否仍允许执行；
- Prefetch 和并发按任务成本配置；
- 邮件按 `message_key` 唯一；
- 同一 ContentItem 的相同 Prompt/模型处理使用稳定 idempotencyKey；
- 同一订阅时间窗口使用唯一约束。

## 12. 安全

- RabbitMQ 用户按生产者和消费者最小权限配置；
- Management UI 仅开发或受保护网络访问；
- 消息不包含 API Key、SMTP 密码、Cookie 或正文大文本；
- 日志限制 payload 大小并脱敏；
- Agent 写事件包含调用者和审批引用。

## 13. 可观测性

指标至少包括：

- Ready/Unacked；
- 发布成功率和 Confirm 延迟；
- 消费吞吐和耗时；
- 重试数量；
- DLQ 数量和最长滞留；
- Inbox 重复命中；
- Outbox 未发布数量和最老事件；
- 任务成功率；
- Worker 心跳和并发。

告警包括 Outbox 滞留、队列积压、DLQ 新增、Consumer 缺失、失败率异常和外部 Provider 连续失败。

## 14. 验收场景

1. 数据库提交后 RabbitMQ 暂不可用，恢复后事件仍发布；
2. Publisher Confirm 超时导致重复发布，消费者只执行一次；
3. Worker 提交前崩溃，消息重新投递并成功；
4. SMTP 暂时失败，按 1/5/30 分钟重试；
5. 参数错误不进入延迟重试；
6. 超过最大次数进入 DLQ；
7. 管理员可查看并重放失败任务；
8. 邮件、Embedding 和 LLM 不产生重复副作用；
9. traceId 串联 API、Outbox、RabbitMQ、Worker 和模型运行。
