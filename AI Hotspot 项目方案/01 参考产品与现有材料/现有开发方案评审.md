# 现有开发方案评审

> 文档状态：草案  
> 评审对象：项目根目录 `AI_PULSE_DEVELOPMENT_SPEC.md`

## 1. 总体判断

现有方案覆盖产品、信源、采集、内容处理、事件、RAG、Agent、数据、接口、安全、测试和里程碑，信息量较完整，适合作为需求知识库。但它同时承担 PRD、架构设计、数据库草案、接口草案和开发指令，导致不同层级的内容混在同一文件中。

新方案不应舍弃旧文档，而应将其拆分、验证、纠错并重新建立依赖关系。

## 2. 值得继承的内容

### 2.1 产品方向

- 资讯、知识研究、Agent 和管理后台的整体构想；
- 一手来源优先；
- 同一事实需要事件级聚合；
- RAG 必须提供真实引用；
- 管理员能够运营信源；
- 邮件或协作工具订阅；
- 旧方案包含微信公众号摘要与导入设想；该能力已根据最新范围决策移出 MVP，仅作为历史评审记录。

### 2.2 工程原则

- 原始数据、标准化内容、事件和知识切片分层；
- SourceEntity 与 SourceEndpoint 分离；
- Connector 统一接口；
- 所有外部任务具备超时、重试、幂等和审计；
- AI 运行保存模型、Prompt、输入输出、Token、费用和延迟；
- Agent 写操作使用服务端权限和人工审批；
- 首期避免 Kubernetes、Kafka 和 Elasticsearch 等不必要复杂度。

### 2.3 技术方向

- Next.js、Spring Boot、FastAPI 的职责分层；
- PostgreSQL、pgvector、Redis、MinIO 的本地完整架构；
- 旧方案曾建议 Redis Streams 承担异步任务；最新正式技术决策已改为 RabbitMQ，Redis 不再承担核心可靠任务队列；
- FTS、向量检索、事件折叠和 Rerank 组成混合检索；
- 使用离线 Fixtures 测试 Connector；
- 使用 Citation Precision、Faithfulness 和 Filter Compliance 评测 RAG。

## 3. 必须重写的内容

### 3.1 产品层级需要重新排序

旧方案将资讯、RAG、Agent 和管理端并列呈现，容易让产品核心模糊。新方案需要明确：

1. 资讯产品是用户第一入口；
2. 采集、处理和事件是产品基础；
3. RAG 和 Agent 是建立在可信数据上的增强能力；
4. 管理后台服务于持续运营，而非单独产品。

### 3.2 数据链路需要细化

旧方案使用 `RawDocument` 同时表达一次原始响应和一篇原始文章，无法清晰处理“一个 RSS 响应包含多条文章”。新方案应拆为：

```text
FetchJob
→ FetchArtifact
→ RawEntry
→ ContentItem
```

### 3.3 内容与事件关系需要调整

旧方案对内容和事件关系描述不完全一致。已确认一篇内容可以关联多个事件，因此必须设计显式的 `ContentEventRelation`，保存关联角色、置信度、理由和审核状态。

### 3.4 缺失的数据领域需要补齐

旧方案只列出部分核心表，以下对象尚未完整设计：

- 用户、角色和权限；
- Topic、Entity、Tag；
- 内容与事件多对多关系；
- 收藏和已读；
- 报告和日报版本；
- 邮件模板、订阅运行和投递日志；
- 审批和审计；
- Prompt 与模型路由版本；
- Outbox 或可靠事件发布；
- 内容纠错与下架请求。

### 3.5 页面规格不够支持原型和开发

旧方案提供路由表，但缺少每个页面的：

- 目标用户；
- 页面区块；
- 字段来源；
- 交互行为；
- 权限；
- 加载、空、异常和无权限状态；
- 响应式规则；
- 页面级验收条件。

### 3.6 API 仍是端点清单

旧方案缺少完整请求响应、分页、排序、权限、并发控制、版本兼容和错误矩阵。正式 API 设计需要建立 OpenAPI 合同并与页面和数据表互相追踪。

### 3.7 评分公式不能直接视为定案

旧方案给出固定权重，但没有训练样本、人工标注或离线评测支持。新方案应先定义评分维度和解释方式，再通过真实样本确定权重；固定数字仅能作为实验初值。

### 3.8 模型参数不能过早固定

FTS Top 40、Vector Top 40、Rerank Top 8 等可作为实验起点，但必须通过评测集调整，不应成为不可修改的产品规则。

## 4. 需要补充证据或决策的内容

- 目标用户优先级和是否公开注册；
- 公开内容池准入规则；
- 受限正文是否进入私有索引；
- 默认模型供应商和费用预算；
- 本地电脑硬件和并发能力；
- 首批正式信源及其授权、稳定性和采集方式；
- 邮件服务商；
- 后续部署目标。

## 5. 不应直接继承的内容

- AI PULSE 品牌；
- 示例中虚构或未来时间的资讯内容；
- 未验证的具体信源 DOM、Feed 和接口；
- 没有数据支撑的固定评分权重；
- 将原型中的模拟指标当作验收基线；
- 将 AI HOT 公开表现推断为其内部采集技术。

## 6. 新方案拆分方式

旧文档内容将按以下归属迁移：

| 旧内容 | 新文档领域 |
|---|---|
| 产品定义、用户价值、MVP | 产品方案 |
| 页面、视觉和流程 | 信息架构与原型 |
| 信源、采集、内容、事件 | 业务领域设计 |
| 技术栈、服务职责、仓库 | 系统架构设计 |
| 表结构和关系 | 数据库与数据治理 |
| API 和异步事件 | 接口与任务设计 |
| 摘要、去重、RAG、Agent | AI 能力设计 |
| SSRF、权限、版权 | 安全权限与内容合规 |
| 测试、指标、告警 | 测试运维与质量保障 |
| 里程碑和任务 | 开发与交付计划 |

## 7. 结论

旧方案的价值在于覆盖面，而新方案的目标是建立清晰边界、可验证规则和可追踪实现。拆分不是格式调整，而是一次完整的产品与系统再设计。
