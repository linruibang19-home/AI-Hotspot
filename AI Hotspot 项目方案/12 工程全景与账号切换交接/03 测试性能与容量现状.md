## 3. 已建立的正式本机基线

`scripts/load/` 已提供固定 k6 版本、公开读取、RAG、Worker、资源采样和摘要脚本；首份报告见 [PERF-01 本地性能与容量基线](../10%20测试运维与质量保障/PERF-01本地性能容量基线.md)。原始产物保存在已忽略的 `artifacts/load/<run-id>/`。

以下仍为目标环境待验证项：

- Linux 目标机 50 VU 持续 30 分钟 soak；
- 首个 RAG 流式 token <5s（当前仍为同步完整响应）；
- 管理查询 < 1s；
- Worker 失败重试、索引重建和 RabbitMQ 中断后的积压恢复；
- PostgreSQL 连接池峰值、慢 SQL、锁等待、磁盘 IOPS 与 pgvector 召回/延迟曲线；
- Redis Session 命中率、MinIO 并发读写和生产 SMTP 投递速率；
- Agent 长任务、取消、重试、审批过期和断点恢复。

## 4. PERF-01 运行规则

1. 只对 Docker Compose 栈的 Nginx `:8088` 入口发压，不绕过 Web/Core。
2. 新建 `scripts/load/` 并提交版本化的场景、阈值和数据准备说明；测试产物写入已忽略的 `artifacts/load/`。
3. 先做 1/10/25/50 并发的公开读基线，再测登录会话、搜索、RAG 和管理查询；不用公开数据写入型 Mock 增压。
4. 记录 P50/P95/P99、错误率、吞吐、容器 CPU/内存、DB 连接/慢 SQL、RabbitMQ 队列和外部 Provider 阶段延迟。
5. RAG 压测分两层：固定黄金集的质量+延迟回归；有严格 QPS/成本上限的外部 Provider 小并发。不得为了“压测”无限调用付费模型。
6. 压测后恢复安静期，检查死信、Outbox/Inbox、索引一致性和公开 Mock=0。

## 5. 性能判定的正确方式

- 不将 Docker Desktop 某一秒 CPU 图当成压测结果；
- 不把空闲健康当成高并发稳定；
- 不把“最近 20 条”与“24 小时/7 天”混成同一指标；
- 不在没有固定数据集、预热和外部 Provider 标识时对比优化前后数字。
