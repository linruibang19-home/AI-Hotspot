# AI Hotspot 数据库详细设计与迁移顺序

> 文档状态：M6 实现基线（2026-07-18）；PostgreSQL 16 + pgvector，DDL 由 Flyway 管理。字段级中文说明见《数据库表全景与字段中文说明》。

## 1. 公共约定

- 主键 UUIDv7；金额以整数最小单位；分数 `numeric(5,2)`；时间 `timestamptz`；邮箱 `citext`。
- 所有可变聚合含 `version bigint not null default 0`，乐观锁更新。
- 业务枚举使用 `varchar + check`，便于滚动升级；JSONB 仅存 Connector/Provider 扩展配置。
- `created_at/updated_at` 由数据库默认 UTC；软删除使用明确业务状态，不用通用 `deleted` 布尔。
- 表名 snake_case；外键命名 `fk_<table>__<target>`；唯一约束命名 `uq_<table>__<fields>`。

## 2. Schema 与所有权

| Schema | 数据 | 写入者 |
|---|---|---|
| `iam` | 用户、邀请、角色 | Core API |
| `source` | 信源、Endpoint、采集任务 | Core + Crawl Worker 受控回写 |
| `content` | 内容、评分、重复、事件、主题实体 | Core；Worker 写暂存结果 |
| `knowledge` | 数据集、Chunk、向量 | Knowledge Worker |
| `research` | 对话、消息、引用、研究任务 | AI API/Core |
| `automation` | 订阅、投递、Agent、审批 | Core/Workers |
| `governance` | 反馈、审计、模型 Prompt | Core |
| `messaging` | Outbox、Inbox、死信 | 各服务限定表 |

生产角色按 Schema 和表授权，不使用共享超级用户。

## 3. 关键字段补充

### 内容

`content.content_item` 增加：`source_version`、`policy_snapshot jsonb`、`score_config_version`、`processing_version`、`published_revision`、`unpublished_reason`。`canonical_url_hash bytea` 用于可控长度唯一性；正文只保存 Object Key 和 Hash。

公开列表部分索引：

```sql
create index ix_content_public_feed
on content.content_item (published_at desc, id desc)
where publication_status='PUBLISHED'
  and visibility='PUBLIC'
  and duplicate_of_id is null;
```

`featured=true` 必须伴随 `publication_status=PUBLISHED`、`visibility=PUBLIC`、`fact_status<>DEBUNKED`，由业务和约束共同保证。

### 事件关系

`content.event_cluster` 含 `first_seen_at`、`last_seen_at`、`primary_content_id`、`cluster_version`、`merge_target_id`。主条目用延迟外键；每个事件的 PRIMARY 关系用部分唯一索引保证。

跨事件表 `content.event_relation(event_from_id,event_to_id,relation_type,confidence,evidence,review_status)`；用规范化方向和唯一约束避免 A-B/B-A 重复。

### 知识权限

`knowledge.dataset_acl(dataset_id, subject_type, subject_id, permission)` 与数据集所有权共同生成允许集合。Chunk 复制 `visibility_scope` 只用于加速，不作为唯一授权真相。检索事务先构造有权 dataset ID，再在该集合中执行 FTS/向量。

### 邮件与退订

`automation.email_delivery.message_key` 唯一；`unsubscribe_token` 只存 Hash、用途、到期和使用时间。投递前查询订阅当前状态，避免退订与队列竞争。

## 4. 分区与保留

MVP 仅对高增长表预留按月分区接口，不提前分区：`fetch_job`、`model_run`、`audit_log`、`email_delivery`。到单表千万级或维护窗口明显受影响再启用。原始响应默认 30 天、失败响应 90 天、审计至少 180 天；正式运营前由合规评审确定最终期限。

## 5. 迁移顺序

1. `V001`（已执行，M1）：扩展与八个业务 Schema。
2. `V002`（已执行，M1）：基础用户/邀请码、Outbox、Inbox 和死信。
3. `V003`（已执行，M2）：角色权限、用户角色、信源主体、Endpoint 和审计。
4. `V004`（已执行，M3）：FetchJob、FetchArtifact、RawEntry 采集链路。
5. `V005`（已执行，M3）：ContentItem、模型运行和公开发布基线。
6. `V006`（已执行，M4）：Connector 正式目录及 X RESERVED 扩展契约。
7. `V007`（已执行，M4）：测试信源与正式信源隔离。
8. `V008`（已执行，M5）：质量维度、去重、事件、实体标签、工单治理。
9. `V009`（已执行，认证增量）：公开邮箱验证码注册与登录。
10. `V010`（已执行，M6）：全文搜索、38 个主题、报告编辑发布和服务端收藏。
11. `V011`（计划，M7）：知识数据集、ACL、Chunk、向量、研究会话与引用。
12. `V012`（计划，M8）：订阅、运行、邮件投递与退订。
13. `V013`（计划，M9）：Agent、步骤、工具调用、审批、模型路由与 Prompt。
14. `V014+`（计划，M10）：基于真实负载的生产索引、保留、备份和运维配置。

每个迁移只前进；回退通过新的补偿迁移。大索引生产创建使用独立迁移与 `CONCURRENTLY` 策略。

## 6. 数据一致性测试

- 公共查询无法返回未发布、私有、重复从条目或 DEBUNKED。
- 一个事件不可能存在两个 PRIMARY；一订阅窗口不可能存在两个 Run。
- Outbox 与业务数据同时提交；Inbox 防止同一消费者重复副作用。
- PRIVATE_RAG 删除后 Chunk、FTS、向量与 MinIO 对象最终一致清理。
- 邀请码、退订 Token 和 Provider 密钥无明文长期存储。
