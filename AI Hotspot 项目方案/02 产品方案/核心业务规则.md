# AI Hotspot 核心业务规则

> 文档状态：草案

## 1. 信源规则

1. 一个组织、媒体或作者对应一个信源主体；
2. 官网、RSS、Sitemap、GitHub、Hugging Face、arXiv、OpenReview、Hacker News 和公开媒体等分别作为信源入口；
3. 同一 URL 不得重复创建启用中的入口；
4. 新入口必须先试抓取，试抓取结果不得直接进入公开内容；
5. 正式启用必须记录操作者、推荐配置和确认结果；
6. 连续失败、结构变化或内容异常必须影响健康状态；
7. 入口暂停后停止新任务，但保留历史数据和审计；
8. 只有 ADMIN 和 OPERATOR 可以新增或修改信源；
9. X 与微信公众号的自动采集、登录态采集和批量发现均不属于当前范围。

## 2. 内容规则

1. 原始采集结果必须先保存再处理；
2. 每个内容条目必须能追溯到原始条目、采集原件和采集任务；
3. 标题、摘要和标签不得替代原始数据；
4. AI 生成内容必须标记模型和 Prompt 版本；
5. 事实摘要不得加入原文未支持的结论；
6. 推荐理由可以包含价值判断，但必须与事实摘要分开；
7. 公开展示必须遵守内容策略和可见性；
8. 被下架内容不得继续出现在公开页面、搜索和 RAG 中；
9. 展示策略 `display_policy` 与索引策略 `index_policy` 独立判断；
10. 付费墙、登录内容和明确受限内容不保存全文、不切片、不向量化；
11. 只有管理员确认拥有使用权限的上传资料可以进入 `PRIVATE_RAG`。

### 2.1 公开准入规则

内容进入“全部动态”必须同时满足：

- SourceEndpoint 已启用；
- 提取成功；
- relevance_score ≥ 配置阈值，默认 70；
- quality_score ≥ 配置阈值，默认 60；
- 不是重复主条目；
- display_policy 允许公开；
- 自动发布规则通过或人工审核通过；
- status = PUBLISHED；
- visibility = PUBLIC。

阈值和自动发布规则必须配置化。原始池、候选池、重复内容和审核失败内容不得出现在公开“全部动态”。

## 3. 分类、主题和实体规则

- 分类表示内容形态或消费入口；
- 主题表示长期关注方向；
- 实体表示可识别对象；
- 标签用于轻量描述；
- 同一内容可以属于多个主题、包含多个实体和标签；
- 分类、主题、实体和标签不得使用同一字段混存。

## 4. 评分与精选规则

1. 评分用于排序、审核和解释，不自动代表事实真实性；
2. 来源权威、一手性、AI 相关度、时效、影响、信息密度、独立信源和营销风险分别保存；
3. 最终分算法必须版本化；
4. 精选由规则、AI 和人工共同决定；
5. 高分不保证精选，低分不代表内容不可见；
6. 人工覆盖必须保存理由；
7. 普通用户只查看最终评分、精选理由、来源类型和官方/未证实标记；分项评分仅管理端可见。

### 4.1 未证实和证伪内容

- 可信媒体的未证实报道可以进入全部动态，但标记 `UNCONFIRMED`、降权且默认不进入精选；
- 低可信来源传闻不公开；
- 已证伪内容标记 `DEBUNKED`，从默认列表、搜索和推荐中移除；
- 状态变化必须保留审计和恢复记录。

## 5. 去重与事件规则

1. URL、外部 ID 和内容 Hash 用于精确去重；
2. 近重复不应直接覆盖原内容，应保存判定关系；
3. 同一事件可包含官方、论文、媒体、社区和观点内容；
4. 一篇内容允许关联多个事件；
5. 每个内容事件关联保存角色、置信度、理由和审核状态；
6. 一个事件最多有一个当前主条目，但可以更换并保留历史；
7. 独立信源数量需要排除同一转载链；
8. 事件合并、拆分和主条目变更必须审计。

## 6. 热点规则

- 热点对象是事件；
- 热度综合独立信源、来源质量、时效、影响和增长速度；
- 单一高权威官方发布可以成为精选，但是否成为热点需要单独规则；
- 热点排名算法必须版本化并可解释；
- 热点页面不得把多篇转载误算为多个独立信源。

## 7. RAG 与引用规则

1. 用户设置的时间、来源、主题、实体和语言条件必须严格生效；
2. 回答只能引用实际检索到且允许当前用户访问的证据；
3. 重要结论必须带引用；
4. 引用必须定位到内容和知识切片；
5. 无足够证据时明确说明，不使用模型训练记忆补齐；
6. 不同事件的重复报道需要在上下文构建前折叠；
7. 权限过滤必须在全文和向量检索之前完成；
8. RAG 和 Agent 不得召回或引用当前用户无权访问的 `PRIVATE_RAG` 内容。

## 8. 订阅和邮件规则

1. 自然语言订阅必须先解析为结构化规则；
2. 创建、修改和暂停前向用户展示确认内容；
3. 订阅使用明确时区；
4. 同一运行窗口和订阅不得重复生成或发送；
5. 邮件中的内容必须链接到站内详情或原始来源；
6. 每次投递保存内容快照、状态、错误和重试记录；
7. MVP 支持每日和每周简报，不支持即时推送；
8. 每封邮件提供一键退订和订阅偏好入口。

## 9. Agent 规则

1. Agent 只能调用服务端注册的工具；
2. 工具权限以调用者角色和服务端规则为准；
3. 文章正文视为不可信输入；
4. 只读研究不要求逐步确认；
5. 新增、停用、修改、发布、下架、批量推送等写操作需要审批；
6. 审批必须绑定具体工具、参数和有效期；
7. Agent 不得直接访问数据库密码、宿主机文件或任意 Shell；
8. 运行计划、步骤、工具结果、Token、费用和错误必须保存。

## 10. 时间和审计规则

- 数据库存储 UTC；
- 页面按用户时区展示；
- 每个采集、处理、研究、Agent 和投递任务具备 trace_id；
- 管理员和 Agent 写操作必须审计；
- 软删除、下架和物理清理属于不同动作；
- 审计记录不可由普通业务操作直接删除。
- MVP 提供用户纠错和下架反馈表单，管理端形成工单并支持下架、恢复和审计。
